# AI ASSISTANT GUARDRAILS & INVARIANTS: PI KIOSK WIDGET BOARD

You are an expert embedded web UI engineer. Your goal is to generate modular code for an iPadOS-style kiosk dashboard running full-screen on a Raspberry Pi 4 inside Chromium.

You MUST strictly adhere to the following architectural, performance, and scope guardrails.

---

### 1. SCOPE & TECH STACK INVARIANTS (FORBIDDEN SCOPE)
- **Primary Languages:** Vanilla HTML5, modern CSS3, and standard modern ES6+ JavaScript ONLY for the board UI. The server is Python 3 standard library only (`board/`), with no pip packages.
- **FORBIDDEN:** Do NOT use C++, Qt, Electron, Tauri, Python GUI libraries (Tkinter/PyQt), React Native, or heavy full-stack frameworks (Next.js/Nuxt) unless explicitly commanded.
- **FORBIDDEN DEPENDENCIES:** Do NOT introduce build-tool requirements (Webpack, Vite, Babel) or heavy npm dependency graphs for simple UI tasks. All scripts should run natively in standard Chromium without a bundling step.
- **Widget Scope:** The board has eight widgets: **Weather**, **Notes**, **Calendar**, **Games** (Four in a Row, Reversi, Dots and Boxes, Blackjack), **Lights**, the **Roommate Cup** (the weekly Roommate Games competition: it keeps score, it doesn't host the games), **Grocery** (Lidl and Trader Joe's: scanned or searched products with price, quantity and who's asking), and **Spotify** (what the linked account is playing: a round cover with the song under it; display only, no app screen). **Sports** (Arsenal and Tottenham in the Premier League, FA Cup, League Cup and Champions League, Maryland soccer in the Big Ten, and every Champions League match) is deliberately not a widget: it's the page before page 1 (`web/js/apps/sports/page.js`), a game-day strip under the clock (`game-day.js`: a countdown to kickoff, then the score and minute), notifications at the foot of page 1 for Arsenal's and Tottenham's next matches (`next-match.js`, one note when they play each other; page 1 keeps room for them with padding below its grid, which edit mode's `pageGeometry()` subtracts), and the Sports app (every match, the tables, and a match page with line-ups, stats and a timeline). Do not invent new widgets or games unless the user asks for one.

---

### 2. HARDWARE & PERFORMANCE CEILINGS (RASPBERRY PI 4)
The target device is a Raspberry Pi 4 running 24/7 in an ambient room.
- **FORBIDDEN (GPU Killers):**
  - Do NOT use heavy CSS blurs (`backdrop-filter: blur(...)`) across large surfaces or full-page containers. Emulate frosted glass using semi-transparent solid hex/RGBA colors (`rgba(255, 255, 255, 0.85)` or `#1c1c1e`) instead of hardware-intensive blur filters. The Glass theme's cards show a pre-made copy of its wallpaper instead (`apple-wallpaper.js` makes it, `glass.js` lines it up); live blur there is only behind the `?glass=live` test switch.
  - Do NOT use continuous unthrottled canvas animations, unoptimized SVG filters, or multi-layered `box-shadow` animations.
  - Ambient motion (the Blocks scenery) runs on one low-rate `setTimeout` ticker that only writes `transform` on elements already promoted with `will-change`, and stops completely when paused. Do NOT use looping CSS animations for it: measured in Chromium, an infinite `steps()` animation keeps the compositor producing ~60 frames/s even when it only changes once a second. One-shot CSS animations (a tap reaction, a page settling) are fine.
- **Memory & Lifecycle Safety:**
  - Every `setInterval`, `setTimeout`, and event listener must be strictly bounded and cleanable. Never introduce unbounded memory arrays or persistent event listener leaks that could cause Chromium to crash over days of uptime.
  - Keep the DOM light. Virtualize or truncate list items if they exceed 100 elements.

---

### 3. DISPLAY & RESOLUTION INVARIANTS (10-FOOT UI)
The screen is a fixed wall/counter monitor viewed from 3 to 10 feet away.
- **Fixed Viewport:** Assume a 1920×1080 resolution (16:9). Avoid flexible laptop-window behaviors that rely on browser resizing. In this repo `1rem = 20px` on the board (`html` font-size is `min(100vw / 96, 100vh / 54)`), so the board is a 96rem × 54rem canvas.
- **Phones are the one exception:** roommates open the same pages on their phones (QR code in the Grocery and Calendar apps). Below 900px wide (or 560px tall) the compact phone layout applies. Keep it working.
- **No Tiny Typography:** Minimum body text size is 18px–20px. Primary items, headers, and counters must be 24px–36px+ for glanceability.
- **High Contrast:** Ensure all text passes WCAG AA contrast standards against the background. Do not use low-contrast grey-on-dark-grey text.
- **Touch & Hit Targets:** All interactive elements (checkboxes, delete buttons, filter pills) must have a minimum hit area of 48×48px. Never design controls that rely solely on desktop `:hover` states to be visible or functional.

---

### 4. DATA PERSISTENCE & CONCURRENCY
- When generating data storage code, isolate state operations behind a clean API or storage service interface (e.g., `GroceryService.getItems()`, `NotesService.addNote()`).
- Use atomic updates for list actions (toggle item, remove item, add item) rather than blindly replacing the entire state with stale closures.
- **Shared data** (notes, the calendar's own events) is stored in local JSON files on the Pi (`data/*.json`), written atomically by the Python server, and pushed to every screen over one event stream (`/api/events`). UI components only talk to the services in `web/js/services/`.
- **Outside data** (weather, connected calendars) is fetched and cached by the server and shared by every screen. The calendars are read on one background thread (`CalendarSources`) and pushed over the same event stream as the stores, so no screen polls for them.
- **Google Calendar is two-way**, over the REST API with the installed-app (loopback) OAuth flow in `board/google.py` — stdlib `urllib` only, no client library. Google's device flow can't be used: it doesn't allow Calendar scopes. Signing in is restricted to the board's own screen (`is_local_address`), the refresh token lives in `data/google.json` at mode 600, and it is never sent to a screen. `board/ical.py` stays for read-only subscriptions that need no account.
- **Lights** are Zigbee switches reached through Zigbee2MQTT on the Mosquitto broker, using the small MQTT 3.1.1 client in `board/mqtt.py` (no paho). `board/lights.py` keeps the schedules, swapped switches and last light list in `data/lights.json`, keeps what each light is doing in memory only (state reports aren't written to the SD card), runs the schedules on its own thread, and pushes everything over the event stream. Lights are keyed by IEEE address, which survives renaming in Zigbee2MQTT. **When it gets dark** (off by default) switches lights on once a day, between noon and its stop time, when the sun (worked out on the Pi from the board's latitude/longitude) or a picked Zigbee light sensor's illuminance says it's dark; a sensor that goes quiet hands back to the sun.
- **Roommate Cup** (`board/roommate_games.py`) keeps the roommates (name, email, phone; no passwords), the catalog of General and Specialized games, the weekly schedule and every game night in `data/roommate-games.json`. Points are always worked out from the stored results, never stored. Its own thread draws each game night's games on game day (about 3 General to 1 Specialized, see `specialized_chance`) and sends them by email (SMTP) and/or text (Twilio's REST API) through `board/notify.py`, stdlib only. Email addresses and phone numbers never leave the Pi unmasked.
- **Grocery** (`board/grocery.py`) keeps the list, a catalog of every product added (by barcode, with its last price) and the names of who asked in `data/grocery.json`. Prices are whole cents. `board/products.py` looks barcodes up in Open Food Facts and Open Prices and searches Open Food Facts, cached on the Pi. `board/store_products.py` keeps every Trader Joe's and Lidl product in the configured country (`data/grocery-products.json`, refreshed weekly on its own thread) so search predictions are a local prefix match, never a request per keystroke. `board/grocery_images.py` fetches and caches product photos (Open Food Facts hosts only) and stores photos taken on phones (shrunk on the phone first); screens only ever load pictures from the Pi. The phone scanner (`web/js/apps/grocery/scan/`) reads EAN-13/UPC-A, EAN-8 (Trader Joe's own products), UPC-E and QR codes (GS1 Digital Link) with our own decoders, using the browser's `BarcodeDetector` where it has one. Live camera needs HTTPS; on plain http the scanner takes a photo instead. Only the scanner and the phone's Scan button use a real `backdrop-filter`: neither ever renders on the Pi.
- **Spotify** (`board/spotify.py`) signs in with the authorization-code flow and PKCE (client ID only, no secret) over the same loopback redirect as Google, so linking is board-only; the refresh token (Spotify rotates it) lives in `data/spotify.json` at mode 600 and is never sent to a screen, and a revoked one is forgotten so the widget offers Connect again. `NowPlaying` asks what's playing on its own thread (every 5s while playing, 15s otherwise, honouring `Retry-After`) and pushes it over the event stream; its version only moves for a new song, a pause or a seek, and the widget moves the playhead itself on one 1s timer that runs only while playing. Covers come only from `i.scdn.co`, only for songs the board has shown, and are kept in memory (`/api/spotify/art`).
- **Sports** (`board/sports.py`) reads ESPN's public scoreboard API (`site.api.espn.com`, unofficial: everything is checked and shaped into the board's own format, so a change there means less on screen, not a crash) and the Big Ten table from bigten.org's standings page (ESPN has no college tables), stdlib only and no account. One thread reads the schedules hourly and the tables every few hours (and just after a followed match ends), and while a followed match is on, that league's scoreboard every 30s; everything is pushed over the event stream. A match page is ESPN's match summary, fetched by the Pi when a screen opens it (`/api/sports/match`) and kept fresh by the thread while the match is on or someone has it open; its `detail` count in the stream says when to fetch it again. Line-ups are laid out from the formation string (ESPN's position names only decide the order). Crests come only from ESPN's image server, only for teams the board has shown, and are kept in memory (`/api/sports/crest`). Nothing is written to the SD card. ESPN has no player ratings, so the pitch marks goals, assists, cards and substitutions instead.
- **Per-device settings** (theme, which widgets are shown) live in browser `localStorage` behind `SettingsService`, with a versioned schema and safe defaults when the stored value is missing or corrupt.

### 5. CODE OUTPUT RULES
- Deliver complete, fully functional, production-ready code blocks.
- Avoid placeholders, omitted boilerplate, or comments like `// implement logic here`.
- Maintain clean separation of concerns: modular CSS classes (BEM or utility-namespaced) and isolated JavaScript modules for each widget.

## Working in this repo

```bash
python3 run.py      # http://localhost:8080 (add ?kiosk=1 for kiosk behaviour, ?at=19:30 to fake the time)
npm test            # Python unittest + node --test, no packages needed
```

- Each app lives in `web/js/apps/<id>/` (`meta.js` with `id`, `name`, `description`, `widgetSize`, `widgetSizes`, icon; `widget.js`; `app.js` if it opens full screen; `index.js` re-exporting them) with styles in `web/css/apps/<id>.css`. Register it in `web/js/apps/index.js`.
- **Widget sizes (required for every widget, including new ones):** widgets are resized in edit mode, so every `meta.js` exports `widgetSize` (the size it starts at) and `widgetSizes` (every size it can be resized to, listed small to large), both from `mini|small|medium|large` (`SIZES` in `widget-layout.js`). `mini` is one column by two rows on the board (the strip left beside the clock; a 1 × 1 square on Glass) and only suits a widget built for it, like Spotify; support `small`, `medium` and `large` unless a size truly can't work, and make the widget look right at each one in every theme: the host puts `widget--mini`, `widget--small`, `widget--medium` or `widget--large` on the card (and `data-size`), so style each size from those classes in the app's CSS, the way Weather (small is today only) and Games (large rows) do. Lists should fill whatever height they get with `fitRows()`. A size changes while the widget is mounted, so nothing may be built for one size only at creation time. `tests/js/widget-sizes.test.js` checks every app's metadata; check the look by rendering the widget at each size.
- A widget is `createWidget(context) → { node, destroy }`. `destroy()` must remove every subscription, timer, and observer it created, because widgets are added, removed and moved between pages at runtime.
- The home screen is swipeable pages of a 12 × 4 grid (page 1 also holds the clock). Every widget has its own place and size, stored per screen in `SettingsService` as `pages` of placements `{ id, size, col, row }`. The pure functions in `web/js/widget-layout.js` decide everything about them (dropping a widget on a cell and pushing aside what it lands on, resizing in place, adding at the first free spot, repairing saved layouts) and are tested with a long randomized run that checks nothing ever overlaps, leaves the grid or covers the clock. Screens saved before placements are laid out once in their saved order (ordered packing, also in that file). Never rely on CSS auto-placement for widget positions.
- Swiping right on page 1 brings in the Sports page (`web/js/side-page.js`), the way the page before an iPhone's home screen works. It isn't one of the pager's pages: the pager hands it right-swipes that start on page 1 (as it hands vertical drags to the app library), and it has its own dot before the page dots, so page indexes, placements and edit mode never include it. It follows the finger one for one and settles with the same spring, moving only `transform`; it stays shut in edit mode and while the app library is up, and phones don't get it (they have the Sports app).
- Edit mode (long-press a widget, or **Edit home screen** in the menu) works like an iPhone's, in every theme: drag a widget anywhere and the others move out of its way live; push it against the side of the screen (or hold your finger near it) and the pages peek, then carry it to the next page. Resizing is a stretch, not a button: pull the corner bracket and the widget follows the finger between its smallest and largest sizes while its slot shows the size it will snap to on release (keyboard users press the corner to step through sizes). Edit mode has no jiggle animation.
- There's no dock. Every app with an `app.js` is in the app library (`web/js/app-library.js`): swipe up on the home pages (the pager hands it vertical drags, so swipes, long-presses and this never fight), from the bottom edge or the page dots, or scroll the mouse wheel down; there's deliberately no button or hint for it. It follows the finger one for one and settles with a spring (a CSS `linear()` easing from `spring()` in `swipe.js`) run as a Web Animation, so the compositor drives it; only `transform` and `opacity` change, the scrim is solid (in Glass, the pre-made frosted wallpaper copy, never a live blur), it stays shut in edit mode, and a closing app shrinks back into its widget if that's on the page in view. Phones don't get it; their home screen is already the apps.
- Pure logic lives in node-testable modules (layout, swipe maths, sky, critter director, game rules); DOM modules can't be imported in node because `ui.js` touches `matchMedia`.
- A game's state is only `{ kind, vsComputer, moves }` and everything else is replayed from it, which is how a saved game is checked. Blackjack deals cards, so it also carries a `seed` its decks are shuffled from — never store the dealt cards. A rules module can opt out of the shared frame with `MODES: false` (no sides to pick) and `UNDO: false`, and reword the panel with `headline()`, `scoreText()` and `summaryText()`.
- Themes are `data-theme="light|dark|blocks|apple"` on `<html>` (Blocks also sets `data-night`). `apple` is shown as "Glass" in the menu; its overrides live in `web/css/apple.css`, it uses the bundled Inter (`web/fonts/inter/`, no CDN) and it lays pages out in iOS widget units (`LAYOUTS.apple` in `widget-layout.js`: a 4 × 2 grid, small 1 × 1, medium 2 × 1, large 2 × 2). `SettingsService` keeps a separate `applePages` arrangement so switching themes never reshuffles the board layout. Colors come from tokens in `web/css/tokens.css`; never hard-code a color in a component that should change with the theme. Game boards use their own fixed colors, checked for 3:1 contrast.
- **Copyright:** the Blocks theme is an original blocky world. Its critters (cat, fox, slime blob, robot) are our own pixel art. Don't copy Mojang/Minecraft (or Nintendo) characters, mobs, textures, fonts or names, and don't use trademarked game names in the UI ("Four in a Row", not the brand name).
